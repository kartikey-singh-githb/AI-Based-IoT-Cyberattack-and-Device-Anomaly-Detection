# ML Methodology

This document explains how the detector works, why it is shaped the way it is,
and what its outputs do and do not mean.

## 1. Problem framing

We detect *unusual device behaviour* in a telemetry stream without labels at
inference time. This is an anomaly-detection problem, not a supervised
classification problem: attack traffic is rare, evolving, and unavailable in
advance. The model answers one question:

> Is this message (in the context of this device's recent history)
> statistically unusual compared to the baseline it was trained on?

It does **not** answer "is this an attack?". A detection may equally be a
sensor fault, firmware change, maintenance window, or legitimate behaviour
drift. Every event is therefore labelled `suspicious` or `critical` and
requires human investigation. The API, the alert text and the dashboard say
this explicitly.

## 2. Feature engineering (`stream` space)

Features are computed per device from a sliding window
(`P310_FEATURE_WINDOW_SIZE`, default 30 s) of its recent messages, in
`backend/app/ml/feature_engineering.py`. 33 features in four groups:

| Group | Features | Rationale |
|---|---|---|
| Timing | `message_rate`, `inter_arrival_mean/std/max`, `last_gap`, `gap_ratio`, `gap_z`, `is_burst`, `is_stall` | Floods compress gaps; blackouts stretch them. Ratios are device-relative (divided by the device's expected interval), so a slow thermometer and a fast meter are judged on their own terms. |
| Persistence | `trailing_burst_ratio`, `trailing_stall_ratio`, `missing_message_ratio` | A single short gap is noise; six consecutive short gaps are a flood. Persistence features keep the signal after the window mean has adapted. |
| Payload / status | `sensor_coverage`, `reading_count`, `status_change_rate`, `status_degraded`, `status_changed`, `connection_attempts`, `connection_attempt_rate`, `payload_bytes` | Connection storms and auth failures show up as attempt bursts; degraded status and shrinking payloads are independent corroborating signals. |
| Sensor values | per-channel value and `_dev` (z-score vs window mean) for `temperature`, `humidity`, `energy_w`, `voltage`, `current_a`, `rssi`, plus `max_sensor_delta` | Sensor spikes are the most direct anomaly type; `_dev` is computed against the device's own window, not a global scale. |

**No leakage**: only information available when the message arrives is used —
no future values, no labels, no cross-device statistics. The same extractor
serves online inference and offline training (`extract_dataset_features`
replays a CSV through the identical per-message function), so train/serve skew
is structural, not a matter of discipline.

## 3. Model

`sklearn.ensemble.IsolationForest` (`backend/app/ml/anomaly_detector.py`).

* `contamination` (`P310_ML_CONTAMINATION`, default 0.05) sets the estimator's
  offset during fitting.
* The **decision threshold** used at inference is *not* the estimator's
  default. It is calibrated as the `P310_ML_FLAG_QUANTILE` (default 5 %)
  quantile of the decision scores observed on the training data. This makes
  the expected flag rate predictable and independent of the estimator's own
  internal offset. Setting `P310_ML_ANOMALY_THRESHOLD` to a non-zero value
  overrides the calibration.
* **Severity bands** are measured the same way: `critical_level` is the
  `flag_quantile × 0.25` quantile (default 1.25th percentile) of training
  scores; anything below the threshold but above it is `suspicious`. Bands are
  never hand-picked constants.
* A per-feature baseline (mean/std from the training matrix) is stored so each
  detection can be explained with `top_deviations` — the largest z-scores
  against baseline, used for the human-readable description only, never for
  the decision itself.
* Per-device cooldown (`P310_DETECTION_COOLDOWN_S`) rate-limits *persisted*
  events so a flood cannot exhaust the database; scoring still happens on
  every message.

## 4. Training data

The default training set is generated by `backend/app/data/synthetic.py`:

* 6 device profiles (thermostat, camera, meter, …) with plausible sensor
  baselines, spreads, clamps and a slow sinusoidal drift term.
* 5 scenario types (`message_flood`, `sensor_spike`, `telemetry_blackout`,
  `connection_storm`, `unauthorized_access`) applied to ~8 % of rows, matching
  the class imbalance of real intrusion-detection data.
* Deterministic for a given seed, so training runs are reproducible.

**Labels are used only for held-out evaluation.** The estimator is fitted on
the full stream *including* the contaminated rows — exactly what it faces in
production, where no labels exist. Evaluation metrics (accuracy, precision,
recall, F1, ROC-AUC, confusion matrix) are computed on a stratified held-out
split and reported by `GET /model` with `metrics_are_measured=true`. Without a
label column, `metrics` is empty and `metrics_are_measured=false` — no
fabricated numbers.

## 5. Public datasets and the `dataset` feature space

`CICIoT2023` and `MQTT IoT IDS 2020` describe **flow/packet statistics**,
not the per-message sensor readings the live pipeline sees. A model trained on
those features cannot score live telemetry (the inputs don't exist), so it is
trained in a separate `feature_space="dataset"` and the runtime detector
**refuses** to load it for live inference. This is deliberate: silently
serving a model on the wrong features would produce confident nonsense.
See `data/datasets/README.md` for how to obtain and load them.

## 6. Caveats (read before showing this to anyone)

1. **All data in this project is simulated.** Devices are virtual; every
   telemetry row carries `is_synthetic=true`.
2. **A detection is not an attack.** Isolation Forest finds statistically
   unusual records. Investigate; don't assume.
3. **Baseline drift.** The model is static until retrained. A legitimate
   change in device behaviour (new firmware, seasonal load) will produce
   detections until the model is retrained on post-change data.
4. **Threshold calibration is training-distribution-specific.** If you retrain
   on a different dataset, expect the flag rate to track the configured
   quantile on *that* data, not on your live traffic.
5. **Determinism.** Training is seeded (`P310_ML_RANDOM_SEED`); identical
   inputs produce identical models. Live scoring has no randomness.
